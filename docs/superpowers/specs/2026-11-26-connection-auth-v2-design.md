# 连接认证 v2 设计

日期：2026-11-26
状态：待审

## 1. 为什么做

2026-11-26 的只读审查（`/Users/admin/min/outputs/kkdesk-review-20261126/report.md`）里还剩 4 个问题没修，都和协议有关：

| 编号 | 问题 | 根源 |
|---|---|---|
| 高 1 | 跨网连接时，控制端无法确认对方真是那台电脑 | 应答 SDP 没有被控端签名；被控端掉线后，别人可以用同一个设备码注册 |
| 高 2 | 局域网的密码验证和 WebRTC 加密连接没有绑定 | 密码挑战和 SDP 交换各走各的；控制端无法验证被控端身份 |
| 高 3 | 短密码的校验值能被离线猜 | LAN 的 HMAC 挑战响应、跨网 SDP 里的 HMAC 都是明文，抓包者或中转服务器都能拿去离线暴力猜 |
| 中 4 | 手机配对可能只在电脑端保存成功 | 最后一条 `committed` 丢了以后，再扫码时电脑回 `already_paired`，手机被要求先去电脑端删除 |

目标：让"连上的就是你想连的那台电脑，且只有知道密码的人能连上"真正成立，而不只是"有个密码"。

## 2. 目标、非目标、反目标

**目标**
- 控制端（电脑和手机）每次连接都验证被控端身份：跨网用设备码，局域网第一次连接时记住对方身份，之后每次核对。
- 密码校验只在已建立、已验证对端身份的 DTLS 加密通道里传输，并绑定本次连接；被动抓包者和跨网中转服务器拿不到任何可以离线猜密码的材料。
- 被控端限制在线尝试：连续输错就暂停一段时间，暂停时长递增。
- 手机配对的最后一步丢了也能恢复：重新扫码即可补存，不需要先去电脑端删除。

**非目标**
- 不兼容旧版本。新旧版本之间无法连接，也不保留旧协议（用户决定：升级后旧的不考虑）。保留旧协议会让攻击者能把双方降级到旧协议，等于没修。
- 不引入 PAKE（CPace/SPAKE2）。方案对比见第 4 节。
- 不改已配对手机走的签名连接（`connectPaired`），它已经用 Ed25519 签名整个交换，包括 SDP。
- 不改设备码的格式和长度。
- 删除跨网"不填密码、由被控端确认"的用法：连接页自 `2b8f5ea` 起密码已是必填，新版控制端不会再发无密码的请求。被控端收到没有 `metaAuth` 的连接一律按超时处理（5.3）。`docs/guide/security.md` 里对应的说法要改，发版说明写明这项变化。

**反目标**（即使功能跑通，出现这些也算失败）
- 出现"新协议失败就退回旧协议"之类的降级路径。
- 身份核对失败时只记日志、照样连接。
- 为了实现这次改动自己手写椭圆曲线或哈希算法。只能用 Go 标准库和手机端现有的 `cryptography` / `crypto` 包。
- 被控端在通过密码校验（或用户确认）之前就开放输入、文件或剪贴板。

## 3. 约束和现状

- 每台电脑都有一把固定的 Ed25519 身份密钥：`internal/pairing/store.go`，`desktop-identity.key`。设备码由公钥算出：`DeviceCode() = "KD-" + base32(sha256(DeviceID(pub)))[:12]`，`DeviceID = sha256("kkdesk desktop id v1\0" || pub)[:16]`。因此任何人拿到一个公钥，都能核对它是否对应某个设备码。
- 身份密钥读不出来时（`pairing.Open` 失败），被控端现在会退回每次启动生成一个临时设备码（`rendezvous.NewCode()`）。v2 里被控端必须有身份才能接受连接，见 5.6。
- 手机端已有 Ed25519（`cryptography: ^2.9.0`）和 SHA-256/HMAC（`crypto: ^3.0.8`）。
- 数据通道：`input-move`、`input`、`meta`、`files`，四个全部打开后 Peer 进入就绪（`internal/session/peer.go`）。被控端的文件服务、输入注入、剪贴板都要等 `Host.handle` 放行后才启动，这一点保持不变。
- 局域网信令：TCP 上每行一个 JSON（`internal/session/signal.go`）。被控端先发 `{"nonce"}`；手机配对路径靠回复 `{"mobile": …}` 分流（`SetMobileHandler`）。v2 必须保留"被控端先发第一条消息、手机配对靠回复分流"这个结构。
- 跨网信令：controller → rendezvous → host 转发 offer，host → rendezvous → controller 转发 answer（`internal/session/remote.go`、`internal/app/remote.go`）。现在的 HMAC 是作为 SDP 属性 `a=x-kkdesk-auth:` 带过去的，rendezvous 原样转发 SDP。
- 已有的修复要保留：改密码后拒绝"已用旧密码验证、还没放行"的连接（`Peer.AuthPassword` + `passwordCurrentLocked`）；局域网 4 路并发握手；单条信令 256 KiB 上限。

## 4. 方案对比（用户已选 A）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 先认设备，再在加密通道里验密码（已选）** | 被控端用身份密钥签名 offer+answer；控制端用设备码（跨网）或已记住的公钥（局域网）核对；DTLS 建好后在数据通道里发绑定本次连接的密码证明；输错锁定 | 不新写密码学代码，两端复用现有 Ed25519 和 HMAC；抓包者和中转服务器拿不到离线猜密码的材料 | 局域网第一次连接、还没记住对方公钥时，如果正好有人在中间冒充，攻击者能拿到一次可以离线猜的证明 |
| B. PAKE（CPace 等） | 密码协议直接防离线猜，首次连接也安全 | 理论上最强 | 手机端 Dart 没有现成实现，要两种语言各写一套椭圆曲线协议，风险和工作量大约是 A 的 2–3 倍 |
| C. 最小改动 | 加设备签名、输错锁定，把临时密码加长到 8–10 位 | 最快 | 离线猜依然可行，高 2、高 3 没有真正修好 |

用户选 A，理由是它在不新写密码学代码的前提下堵住了三个高风险问题。

## 5. 设计

### 5.1 被控端身份签名（修高 1、高 2 的身份部分）

被控端生成 answer 后，用身份私钥签名：

```
hostSig = Ed25519.Sign(hostKey,
    "kkdesk host answer v2\0" || u32len(offerSDP) || offerSDP || u32len(answerSDP) || answerSDP)
```

- `offerSDP` 是控制端发来的完整 offer（含控制端 DTLS 指纹和随机 ICE 凭据，保证每次都不同），`answerSDP` 是被控端返回的 answer（不含签名本身）。
- 签名和公钥（base64url，无填充，与 `pairing.Encode` 一致）一起返回：
  - 局域网：放在 TCP 应答消息里，`{"sdp": answer, "hostKey": …, "hostSig": …}`。
  - 跨网：作为 SDP 属性附在 answer 末尾，`a=x-kkdesk-host-key:` 和 `a=x-kkdesk-host-sig:`（沿用现在 `a=x-kkdesk-auth:` 的做法：WebRTC 会忽略未知属性，rendezvous 原样转发）。控制端验签前先剥掉这两行，剥的规则和现在的 `VerifyRemoteOffer` 一致：只认最后一次出现、必须位于行首。
- 控制端在 `setRemoteDescription` **之前**验签，并核对公钥：
  - 跨网：`DeviceCode(hostKey)` 必须等于用户填的设备码（规范化后比较）。
  - 局域网：见 5.2。
  - 任何一步失败都直接断开，并给出明确提示（见 5.7），不得继续连接。
- Pion 和 flutter_webrtc 都会校验对端 DTLS 证书与 SDP 里的 `a=fingerprint` 是否一致，所以签过名的 answer 等于把 DTLS 对端绑定到了这台电脑的身份上。

### 5.2 局域网首次信任与核对

- 控制端在本地记录"地址 → 被控端公钥"：
  - 电脑：存进现有的地址簿（`internal/config/devices.go`），设备条目新增 `HostKey` 字段。手动输入地址连接时，也按地址在地址簿里查找。
  - 手机：手机端目前**不保存**手动输入的地址（`mobile/lib/main.dart` 的 `_launchLan` 每次临时构造 `Computer(id: 'lan:$address')`，文件传输入口同样不落盘）。新增一份持久存储"地址 → 被控端公钥"，用手机端已有的存储方式（实现者按现有代码选 shared_preferences 或 secure storage）。桌面连接和文件传输两个入口共用这份记录。
- 第一次连接某个地址（没有记录）：接受对方公钥并记下来，连接界面的提示里显示对方的设备码，方便用户和对方屏幕上显示的设备码核对（不强制核对）。
- 之后再连同一个地址：公钥必须一致。不一致时**拒绝连接**，不提供"仍然连接"按钮（我的决定：一键越过等于没核对）。
  - 电脑端提示："这台电脑的身份变了（可能重装了 kkdesk，也可能有人冒充）。如果确认是重装，请在「我的设备」里删除这台设备后重新连接"。手动输入、不在地址簿里的地址，删除方式同样是地址簿里对应的条目（首次连接时会自动加入地址簿，现有行为）。
  - 手机端没有设备列表，所以错误卡片上提供「忘记这台电脑的身份」按钮。点击后弹二次确认，写明"只有确认对方重装了 kkdesk 时才这样做，否则可能连到冒充的电脑"；确认后删除该地址的记录，用户再手动重连，重连按首次连接处理。
- 如果用户在局域网输入框里填的是设备码而不是地址，走跨网流程（现有行为），不受影响。

### 5.3 在加密通道里验密码（修高 2 的绑定部分、高 3）

信令里不再带任何密码相关的东西：删掉局域网的 nonce/mac 挑战，也删掉跨网的 `a=x-kkdesk-auth:`。

Peer 就绪（四个数据通道都打开）后，控制端在 `meta` 通道上发送密码证明：

```
proof = HMAC-SHA256(key = password,
    "kkdesk password v2\0" || sha256(offerSDP) || sha256(answerSDPWithoutSig))
```

- 新增 meta 消息类型（字节值由实现者从未用过的值里选）：
  - `metaAuth`（控制端 → 被控端）：32 字节证明。
  - `metaAuthResult`（被控端 → 控制端）：结果码：成功 / 密码错误 / 暂停中（附剩余秒数）。
- 被控端用临时密码和固定密码各算一遍，常数时间比较，并且两个都算完再判断（沿用 `verify` 的做法）。记下匹配的是哪一个，写入 `Peer.SetAuthPassword`，原有的"改密码后拒绝"逻辑继续生效。
- 被控端在 Peer 就绪后等 `metaAuth`，最多 10 秒，超时断开。收到之前不调用 `handle`，也不处理除 `metaBye` 以外的 meta 消息。现在的 meta 处理会立刻响应 quality/clipboard 等消息，要加一道"未认证不处理"的闸门。clipboard 本来就要等 `handle` 放行后才同步，quality 可以像现在一样暂存。
- 校验失败：发 `metaAuthResult(密码错误)`，然后以"密码错误"为原因关闭连接，并计入锁定计数（5.4）。
- 校验成功：发 `metaAuthResult(成功)`，进入现有的 `handle` 流程。是否还要用户确认，仍由「连接前需要确认」决定。`passwordOK` 对局域网和跨网都为真，因为 v2 里不再有"无密码的旧版控制端"。
- 手机手输密码连局域网走同一套流程。手机端在 meta 通道收到成功结果之前，不得把连接当成已经连上。

### 5.4 输错锁定

- 被控端维护一个全局计数（不区分来源，跨网请求的来源地址都是中转服务器，按来源区分没有意义）：连续 5 次密码错误后暂停 30 秒，之后每多错一次暂停时间翻倍，最长 15 分钟；任何一次成功都会清零。计数只存在内存里，重启 kkdesk 清零（我的决定：持久化的收益很小，还要处理时钟回拨）。
- 暂停期间，被控端仍然完成 WebRTC 握手（否则拿不到 meta 通道来告诉对方原因），但收到 `metaAuth` 后不做校验，直接回 `metaAuthResult(暂停中, 剩余秒数)` 并断开。暂停中的尝试不计入计数。
- 被控端界面在暂停期间显示一条提示："多次密码错误，已暂停接受密码连接 N 秒"。
- 已配对手机走签名连接，不受密码锁定影响。

### 5.5 手机配对恢复（修中 4）

现在的行为：手机扫码后，如果电脑已经存了这台手机的公钥，电脑回 `already_paired`；手机本地没有记录时，会提示"请先在电脑端「已配对手机」中移除后再扫码"。

改为：电脑收到配对请求（扫码 `pair` 和手动配对码 `pair_manual` 两条路，它们在 `internal/app/pairing.go` 里共用 `requestPairing`）时，如果这台手机的公钥已在配对列表里，并且这次请求通过了对应的凭证校验（扫码为 `CodeProof`，手动配对码为现有的配对码校验）和手机签名校验，就直接回 `committed`（附上已存记录的 `bypass` 等字段），与新配对成功时的消息一致，并带上本次交换的 nonce。手机按"配对成功"处理并补存记录。

- 安全性：二维码和手动配对码都只显示在这台电脑的屏幕上，能证明操作的人就在电脑前；手机签名证明是同一部手机。这与重新走一遍配对确认等价，因此不需要再弹确认框（我的决定）。
- 手机端已有记录时（`devices.matchingComputer` 命中），行为不变。
- `already_paired` 不再在这条路径上出现。

### 5.6 被控端必须有身份

身份密钥读写失败时，被控端不接受任何连接，界面显示错误"无法读取本机设备身份：…"，日志写明路径。删除临时设备码的退路（`rendezvous.NewCode()` 用于本机设备码的那部分）。

### 5.7 用户可见的提示

| 场景 | 控制端提示 |
|---|---|
| 跨网设备码与对方身份不符 | "对方不是设备码 KD-… 对应的电脑，已断开" |
| 局域网对方身份变了 | 见 5.2 |
| 签名无效或缺失 | "对方的身份签名无效，已断开（对方可能是旧版本 kkdesk，请两边都升级到最新版）" |
| 密码错误 | "密码错误" |
| 被控端暂停中 | "对方因多次密码错误暂停了连接，请 N 秒后再试" |
| 首次连接某个局域网地址 | 连接提示里显示"对方设备码 KD-…" |

旧版本 kkdesk 连新版，或新版连旧版，都会因为缺少签名或消息格式不对而失败。失败提示要包含"请两边都升级到最新版"。

- `docs/guide/connect-lan.md`、`docs/guide/remote.md`：补充身份变了时的处理、暂停提示。

## 6. 测试要求

每项先写失败的测试，再实现。

- Go 单元测试：签名与验签（被篡改的 offer/answer、换了公钥、设备码不符、属性不在行首）；证明的计算与校验（错密码、绑定的 SDP 不同）；锁定的计数、翻倍、上限、成功清零、暂停中不计数。
- Go 集成测试（`internal/session`、`internal/app`，在本机回环上跑）：
  - 局域网：首次连接记下公钥；第二次连接身份不变则成功、身份变了则拒绝；密码错误；锁定。
  - 跨网：设备码不符被拒（用测试用 rendezvous，让另一把身份密钥冒用设备码注册）。
  - 用临时密码和固定密码连接，两种都要覆盖；改密码后拒绝的回归测试继续通过。
  - 收到 `metaAuth` 之前，被控端不启动文件服务、不注入输入、不同步剪贴板。
- 手机端（Flutter）：证明计算与 Go 的测试向量一致（双方共用一份固定的测试向量文件）；签名校验与 Go 一致；首次信任与身份变化；配对恢复。
- 全部检查：`gofmt -l .` 为空、`go vet ./...`、`go test ./...`、相关包跑 `-race`、`GOOS=linux CGO_ENABLED=0 go vet ./...`、`GOOS=windows` 加 mingw 的 vet、`dart analyze`、`flutter test`。
- 真机冒烟（实现完成后，由用户或执行者在真机上做）：Mac↔Windows 局域网、Mac↔Windows 跨网、手机手输密码连局域网、手机配对恢复。

## 8. 我替用户做的决定（请审阅时确认）

1. 局域网对方身份变了时直接拒绝，不提供"仍然连接"（5.2）。
2. 锁定参数：5 次后暂停 30 秒，每次翻倍，最长 15 分钟；全局计数，不持久化（5.4）。
3. 配对恢复不再弹确认框，扫码或手动配对码加签名即视为确认，两条路都恢复（5.5）。
6. 删除跨网无密码由对方确认的用法（第 2 节非目标）。
7. 手机端新增"地址 → 公钥"存储；身份变了时，错误卡片上提供需要二次确认的「忘记这台电脑的身份」（5.2）。
4. 身份密钥不可用时被控端拒绝所有连接，不再退回临时设备码（5.6）。
5. 首次连接局域网地址时只显示对方设备码供核对，不强制核对（5.2）。
