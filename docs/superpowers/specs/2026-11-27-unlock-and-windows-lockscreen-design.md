# 控制端解锁与 Windows 锁屏远程操作（实施范围）

日期：2026-11-27
状态：用户已同意；本文件是对 `2026-11-26-lockscreen-access-design.md`（下称"锁屏设计"）的补充与本期范围调整

## 1. 为什么

用户在控制中心里想要"解锁"：被控端锁屏后（例如上一个控制端断开触发了"断开后自动锁屏"），控制端能一键解锁继续用。解锁密码由用户决定**存在控制端**（用户这台电脑的钥匙串），被控端不保存任何系统登录密码。

解锁的前提是"特权组件能看到并操作锁屏界面"（锁屏设计第 5 节）。该前提在 macOS 上还没有实测结论（锁屏设计阶段 0 待用户执行）；Windows 有微软文档（LocalSystem 可访问安全桌面的 DXGI 复制）和业界先例支撑。

## 2. 本期范围（调整锁屏设计第 6 节）

- **Windows 被控端**：直接实现锁屏设计第 5 节的 Windows 部分（系统服务 + 锁屏助手 + 本机 IPC + 主进程切换 + 安装/卸载/更新），不再等阶段 0 结果。实现完成后打 Windows 测试包，用户实测即同时验证地基和解锁。
- **macOS 被控端**：本期不实现特权组件，等阶段 0 结果。macOS 被控端在锁屏时如实回报"暂不支持锁屏远程操作"。
- **控制端（macOS 与 Windows）**：实现解锁界面和密码保存（下文第 3 节）。
- 锁屏设计第 5 节中与 Windows 相关的要求（受保护目录、IPC 身份校验、只在锁屏且有会话时工作、不开网络端口、默认不安装）全部适用。

## 3. 解锁功能

### 3.1 控制端

- 被控端回报"已锁屏"时，控制中心出现「解锁电脑…」；未锁屏时不显示。仅查看会话不显示（解锁属于操作）。
- 被控端回报"锁屏但不支持远程操作"（未装组件、macOS 本期）时，菜单项显示为禁用，悬停/说明文字写原因："对方电脑未安装锁屏远控组件" / "对方系统暂不支持锁屏远程操作"。
- 点击后：
  - 已为这台被控端保存过密码：直接发送解锁请求（不再弹框）。菜单里另有「忘记解锁密码」。
  - 未保存：弹框输入"对方电脑的登录密码或 PIN"（锁屏界面要什么就填什么；很多 Windows 默认要 PIN），复选框"记住密码（保存在本机钥匙串）"，默认不勾。
- 保存位置：按被控端身份（认证 v2 的被控端公钥，不按地址或设备码）作为键。
  - macOS：钥匙串（Security framework，generic password，service 名如 `kkdesk.unlock`，account 为被控端公钥指纹）。
  - Windows：凭据管理器（`CredWriteW`/`CredReadW`，`CRED_TYPE_GENERIC`，或 DPAPI `CryptProtectData` 加密存到配置目录；实现者择一，优先凭据管理器）。
  - Linux 控制端：不提供"记住密码"（复选框隐藏），只能手输。
  - 只用系统原生接口（cgo / syscall），**不新增第三方依赖**；确需依赖时停下来问。
- 解锁失败（密码错）时：如果用的是已保存的密码，提示"已保存的解锁密码不正确"，并提供"重新输入"（覆盖保存）和"忘记解锁密码"。
- 控制端不在日志、诊断文件、崩溃信息里写出密码；内存里的密码用完尽量清零（Go 字符串做不到时用 `[]byte`）。

### 3.2 协议（meta 通道，认证通过且 `handle` 放行后才处理）

| 方向 | 消息 | 内容 |
|---|---|---|
| 被控端 → 控制端 | 锁屏状态 | 未锁屏 / 已锁屏且可远程操作 / 已锁屏但不支持（附原因） |
| 控制端 → 被控端 | 解锁请求 | 密码（UTF-8） |
| 被控端 → 控制端 | 解锁结果 | 已解锁 / 密码可能不正确（仍锁屏）/ 不支持 / 尝试过多 |

- 锁屏状态在会话开始时发一次，变化时再发。
- 仅查看会话收到解锁请求一律拒绝。
- 字节值、编码由实现者定，避开已用值。不需要兼容旧版本。

### 3.3 被控端（Windows）

- 收到解锁请求：若未锁屏 → 回"已解锁"（无事可做）；若未装组件或助手不可用 → 回"不支持"。
- 否则把密码交给锁屏助手（经锁屏设计 5.2 的 IPC），助手在锁屏桌面上：先唤醒/收起锁屏幕帘（如按一次空格或 Esc，实现者实测选择），必要时发送 Ctrl+Alt+Del（`SendSAS`，需要相应策略；实现者查清条件，不满足时记录并继续），在密码框输入密码并回车。
- 等系统确认解锁（WTS 会话状态变为未锁定），最多 15 秒；确认后回"已解锁"，主进程切回自身采集（锁屏设计 5.3）；超时回"密码可能不正确"。
- **防止锁死账户**：Windows 有账户锁定策略。每个会话最多 3 次解锁尝试，超过回"尝试过多"；被控端界面记录一条提示。
- 被控端不在日志、IPC 调试输出里写出密码；IPC 缓冲用完清零。
- 解锁请求需要被控端已安装组件（等同于被控端用户已经允许"锁屏时远程操作"），不另设权限开关。

## 4. 测试要求

- 控制端：钥匙串/凭据管理器的保存、读取、删除（集成测试用独立的 service 名，测试结束清理，不碰用户已有条目）；按被控端公钥区分；错误密码流程；Linux 不显示记住。
- 协议：认证前、仅查看、files-only 均拒绝；锁屏状态回报；解锁结果各分支（用假助手）。
- 被控端 Windows：解锁尝试次数上限；超时；密码不进日志（测试里检查日志输出不含测试密码）。
- Windows 特权组件：锁屏设计第 7 节全部要求。
- 全部检查：`gofmt -l .` 为空、`go vet ./...`、`go test -count=1 ./...`、相关包 `-race`、`GOOS=linux CGO_ENABLED=0 go vet ./...`、`GOOS=windows` + mingw 的 vet。
- 产出 Windows 测试包（`scripts/build-windows.sh`）和中文实测说明：安装组件、Mac 控制 Windows、锁屏、看到锁屏画面、用控制中心解锁（含记住密码与错误密码）、卸载组件。

## 5. 我替用户做的决定

1. 密码按被控端公钥保存，不按地址或设备码。
2. 已保存密码时一键解锁；连接时不自动解锁（需用户点击）。
3. 仅查看会话不提供解锁。
4. 每个会话最多 3 次解锁尝试，防止触发 Windows 账户锁定。
5. Linux 控制端不提供"记住密码"。
6. Windows 先做、macOS 等阶段 0；控制端两平台都做。
