# 锁屏可远程操作设计（第一步）

日期：2026-11-26
状态：用户已同意方向；分两阶段，阶段 0 验证完成后必须停下汇报，阶段 1 再实现

## 1. 为什么做

刚上线的"断开后自动锁屏 / 锁屏并断开"（`docs/superpowers/specs/2026-11-26-privacy-screen-and-lock-design.md`）有个硬伤：电脑锁屏后 kkdesk 既采不到画面，也注入不了输入，远程连不回去，必须有人到电脑前输入密码。用户远程控制自己没人的电脑时，这等于锁一次就断一次。

目标：被控端锁屏时，控制端仍能看到锁屏界面、用键盘输入系统密码解锁，然后继续正常远控。

用户提过"记住密码自动解锁"，那是**第二步**，本设计不做，但架构要给它留位置（解锁时由特权组件代输密码）。

## 2. 目标、非目标、反目标

**目标**
- Windows 被控端：锁屏（Win+L、`LockWorkStation`、空闲锁屏）时，控制端能看到锁屏/登录界面并输入密码、按 Ctrl+Alt+Del（如系统要求）。解锁后画面自动切回桌面，会话不断。UAC 安全桌面顺带同样可用。
- macOS 被控端：屏幕锁定时，控制端能看到锁屏界面并输入密码解锁，解锁后会话不断。
- 这项能力需要安装特权组件，由被控端用户在「设置」里主动安装（需要管理员授权），可以卸载。不安装时行为与现在完全一样。

**非目标**
- 记住系统密码、自动解锁（第二步）。
- 用户完全注销后（登录窗口、开机后未登录）的远控。架构上不要堵死，但本期不验收。
- 快速用户切换到别的账户。
- 改变 WebRTC、认证 v2、隐私屏的协议和行为。

**反目标**
- 特权组件对外开放任何网络端口，或接受未经认证的本机连接（本机任意进程都能让它截屏或注入 = 提权漏洞）。
- 特权组件在电脑未锁屏时也在截屏、注入（扩大攻击面）。
- 不装特权组件的用户受到任何影响。
- 安装、更新、卸载失败后留下半装状态（服务注册了但文件没了，或反过来）。

## 3. 现状

- 被控端采集：`internal/capture`（macOS ScreenCaptureKit、Windows DXGI Desktop Duplication），注入：`internal/inject`（macOS CGEvent、Windows SendInput）。都在 kkdesk 主进程（普通用户权限）里运行。
- Windows 锁屏时 DXGI 返回 `ACCESS_LOST`，采集自动重启（`internal/capture/restart.go`）但拿不到画面；`InjectLimits` 已写明普通权限进不了安全桌面。
- macOS 锁屏时采集也失败（隐私屏实现期间在本机实测到）。
- 应用本身：macOS 是 `/Applications/kkdesk.app`（`tan build` + `tan sign`），Windows 是单个 `kkdesk.exe`（`scripts/build-windows.sh`，没有安装程序），有自动更新（`internal/update`）。
- 编码、WebRTC、认证都在主进程里。

## 4. 方案对比

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 只在锁屏时由特权助手代为采集和注入（推荐）** | 主进程照旧负责网络、编码、认证。检测到锁屏后，向特权助手要原始画面（共享内存）并把输入事件转给它注入；解锁后切回主进程自己采集 | 主架构不动；特权代码最少、只在锁屏时工作，攻击面小；不装助手时完全不受影响 | 要做本机进程间通信（画面 + 输入）；切换时画面可能闪一下 |
| B. 整个被控端引擎跑在特权进程里（RustDesk 的做法） | 服务以 SYSTEM / root 运行被控端全部逻辑，界面进程只做显示 | 业界验证过，注销后登录窗口也能控 | 大重构：网络、编码、认证、文件传输全搬进特权进程，攻击面大，现有代码和测试大量改动 |
| C. 不做特权组件，只在锁屏前阻止系统锁屏 | 远控期间禁止自动锁屏 | 很简单 | 不解决"断开后锁屏"后连不回来的问题，与上一个功能矛盾 |

我按用户授权选 **A**：在不重构现有被控端的前提下解决问题，特权代码量和暴露面都最小。B 的"注销后也能控"不在本期目标里。

## 5. 设计（方案 A）

### 5.1 组件

- **Windows**：
  - `kkdesk` 系统服务（以 LocalSystem 运行），由主程序的同一个 exe 以服务模式启动（如 `kkdesk.exe -service`），开机自动启动。
  - 服务负责在当前控制台会话里拉起**锁屏助手**进程：以 SYSTEM 令牌、目标会话号启动（`WTSGetActiveConsoleSessionId` + `DuplicateTokenEx` + `SetTokenInformation(TokenSessionId)` + `CreateProcessAsUser`，桌面 `winsta0\winlogon`），助手内部用 `OpenInputDesktop` / `SetThreadDesktop` 跟随当前输入桌面，做 DXGI 采集和 SendInput 注入。会话切换、助手退出时服务重新拉起。
- **macOS**：
  - 特权组件的具体形态由阶段 0 决定。候选：随 app 打包的 LaunchDaemon（root）+ 运行在 `LoginWindow`/`Aqua` 会话类型的 LaunchAgent，通过 `SMAppService`（macOS 13+，用户在系统设置里批准）注册；或传统的 `/Library/LaunchDaemons` + 管理员授权安装。
  - 阶段 0 必须查清：锁屏状态下，哪种进程（普通用户进程 / root 守护进程 / LoginWindow 会话的代理）能用 ScreenCaptureKit 或 `CGDisplayStream` 拿到锁屏画面，哪种能用 `CGEventPost`（哪一层 event tap）把键盘输入送进锁屏密码框。

### 5.2 主进程与助手的通信

- 只走本机 IPC：Windows 命名管道（ACL 只允许同一交互用户的 kkdesk 主进程，见下）、macOS Unix 域套接字（文件权限 + `getpeereid` / 代码签名校验）。**不开任何 TCP 端口。**
- 认证：主进程必须证明自己是"当前登录用户运行的、签名有效的 kkdesk"。Windows 用管道服务端检查客户端进程的用户 SID 等于当前控制台会话用户，并校验可执行文件路径与服务自身一致；macOS 校验对端 uid 等于当前控制台用户、对端代码签名与自身团队 ID 一致。拿不准的地方阶段 0 汇报。
- 内容：
  - 画面：助手采集原始 BGRA 帧，放进共享内存（双缓冲 + 序号），主进程取走后照常编码发送。
  - 输入：主进程把 `input.Event` 原样转给助手注入。
  - 控制：开始/停止（主进程仅在锁屏时请求开始）、锁屏状态变化通知。
- 助手只在"已锁屏且主进程有活动远控会话并请求"时才采集和注入，解锁或会话结束立即停止。

### 5.3 主进程里的切换

- 锁屏检测沿用隐私屏里已有的实现（macOS `CGSessionCopyCurrentDictionary`，Windows WTS 会话状态），改为可订阅变化。
- 有活动远控会话（非仅传文件）时：锁屏 → 停掉自身采集、改用助手画面；输入改发助手。解锁 → 停助手、恢复自身采集、发关键帧请求。
- 分辨率可能不同（锁屏界面分辨率与桌面一致，但 DPI/多屏布局可能变）：编码器按帧尺寸重建（现有逻辑已支持）。
- 没装助手或助手不可用：行为与现在一样（锁屏时画面中断），控制端显示"对方电脑已锁屏（未安装锁屏远控组件）"。
- 隐私屏：锁屏时遮罩照常撤（现有逻辑），解锁后如果之前开着隐私屏，按现有规则恢复，不改。

### 5.4 安装、更新、卸载

- 「设置 › 安全」新增"锁屏时允许远程操作"：显示组件状态（未安装 / 已安装 / 需要在系统设置里批准 / 版本不匹配），按钮"安装"/"卸载"。
  - Windows：点安装时以管理员身份（UAC 提权）运行 `kkdesk.exe -install-service`，把当前 exe 复制到受保护目录（如 `%ProgramFiles%\kkdesk\`）并注册服务；服务和助手都从这个目录运行（不能从用户可写目录以 SYSTEM 运行，否则任何人替换 exe 即可提权）。
  - macOS：按阶段 0 选定的方式。
- 自动更新：主程序更新后，特权组件版本不一致时提示"锁屏远控组件需要更新"，点一下用管理员授权更新。Windows 服务从受保护目录运行，更新时由提权进程替换文件并重启服务。具体流程阶段 1 计划里细化。
- 卸载：停止并删除服务/守护进程，删除受保护目录里的文件。

`docs/guide/security.md`（特权组件做什么、不做什么、如何卸载）、`docs/guide/control.md`、`docs/guide/faq.md`（锁屏后连不回来怎么办）、发版说明。

## 6. 分阶段

### 阶段 0：可行性验证（必须先做，做完停下汇报）

产出一个可运行的最小验证程序和一份报告 `docs/superpowers/specs/2026-11-26-lockscreen-access-spike.md`：

- **不打扰用户的规则**：本机就是用户正在用的 Mac。**任何会锁屏的步骤、任何需要管理员密码的步骤（安装 LaunchDaemon、`sudo`、系统设置里批准），实现者都不得自己执行**：只准备好脚本和一份中文操作说明（每步做什么、预计多久、怎么撤销），然后停下来交给派单会话，由用户在方便时亲自执行。不需要锁屏和管理员权限的部分（编译、单元测试、读系统文档、`SMAppService` 注册代码的编译）可以直接做。
- **macOS**（脚本由实现者准备，锁屏和提权步骤由用户执行）：
  1. 锁屏状态下，普通用户进程 / root LaunchDaemon / LoginWindow 会话 LaunchAgent 各自能否采到锁屏画面（ScreenCaptureKit、`CGDisplayStream`、`CGWindowListCreateImage` 都试），能否把键盘输入送进锁屏密码框（`CGEventPost` 各 tap 层级）。用自动化脚本在锁屏后几秒内执行、把结果写日志和截图文件，再由人解锁查看。不要把用户的系统密码写进任何文件；验证输入时只输入几个字母、确认密码框收到了字符即可（看截图里圆点数量），不要尝试真正解锁。
  2. `SMAppService` 能否从 kkdesk.app 包里注册所需的守护进程/代理，用户批准流程是什么样。
  3. 结论：macOS 采用哪种组件形态，或者"macOS 做不到"及原因。
- **Windows**（本机无法实测）：
  1. 交叉编译一个验证用 exe（`-spike-service-install` / `-spike-service-uninstall` / 服务模式），服务以 SYSTEM 在控制台会话里拉起助手，助手在锁屏桌面上采一帧 DXGI 画面存为 PNG、并 SendInput 输入几个字母，全部写日志。
  2. 写一份给用户的中文操作说明（以管理员身份安装、锁屏、等 10 秒、解锁、把日志和图片发回、卸载）。
  3. 产物放到 `/Users/admin/min/outputs/kkdesk-lockscreen-spike/win/`。
- 阶段 0 的代码放在独立的验证目录或用构建标签隔离，不进入正式功能路径。

**阶段 0 结束后停下来汇报**：两个平台的结论、推荐的组件形态、对 5.x 节需要修改的地方。由派单会话和用户确认后，才写阶段 1 计划并实现。

### 阶段 1：正式实现

按阶段 0 的结论修订本设计第 5 节，然后：计划 → 逐任务 TDD → 每任务一提交 → 全部检查（gofmt、vet、test、race、Linux/Windows vet）→ 真机验收（Windows 由用户执行）。

## 7. 测试要求（阶段 1）

- IPC 认证：伪造的客户端（不同用户、不同可执行文件、签名不符）被拒绝。
- 切换逻辑：锁屏/解锁事件驱动的采集源和输入目标切换，用假助手做单元测试；会话结束时助手停止。
- 助手只在锁屏且有请求时工作。
- 安装/卸载幂等，失败可回滚。
- 真机：锁屏后控制端看到锁屏界面、输入密码解锁、会话不断；Windows 的 Ctrl+Alt+Del 场景；未安装组件时行为不变。

## 8. 我替用户做的决定（请审阅时确认）

1. 选方案 A（只在锁屏时由特权助手代采集和注入），不做整体搬进特权进程。
2. 先做验证阶段，验证完停下汇报再实现。
3. 特权组件必须从受保护目录运行，只用本机 IPC 且校验调用方身份，不开网络端口。
4. 注销后登录窗口远控、快速用户切换不在本期。
5. 组件需要被控端用户在「设置 › 安全」里主动安装，默认不装。
6. 验证阶段在本机的锁屏、提权步骤一律由用户亲自执行，实现者只准备脚本和说明。
